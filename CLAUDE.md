# CLAUDE.md — Kynetik Build Tracker v2

Read first: `docs/KYNETIK_BUILD_TRACKER.md` (v1 spec, source of truth for behaviour), `docs/PLAN.md` (architecture, schema, settings, decisions D1–D8, phase plan incl. **Phase 3.5** in §7), `docs/PHASE_EMPLOYEE_VIEW_PROMPT.md` (Phase 3.5 brief). **Never invent business rules.** If the spec doesn't cover something, ask the Owner, then record the answer in PLAN.md §0.

## Commands

```bash
npm run dev:all        # local Supabase + reset + seed + .env.local + owner invite + next dev
npm run lint && npm run typecheck && npm test && npm run test:db && npm run build   # what CI runs
npm run seed:generate && npm run deploy:sql  # after editing seed data, defaults or migrations; commit both SQL files (CI checks them)
```

`test:db` needs a Postgres superuser at `TEST_DATABASE_URL` (default `postgres://postgres:postgres@localhost:5432/postgres`). It applies `supabase/tests/shim.sql`, which stands in for the Supabase `auth` and `realtime` schemas, then all migrations, then the seed. Docker isn't needed. In the Claude Code cloud container, run `pg_ctlcluster 16 main start` first. Docker image pulls are blocked there, so `supabase start` doesn't work.

## Layout

- `domain/`: pure TypeScript business rules. ESLint forbids importing React, Next, Supabase or app code here. Every rule takes its parameters from `Settings` (`domain/settings.ts`). Never use constants, and never import `DEFAULT_SETTINGS` inside a rule (defaults are only for seeding and fallback).
- `app/(console)/…`: Admin Console pages. Every page and server action starts with `requireViewer([...roles])`.
- `app/display/[token]` and `app/api/display/[token]/…`: the Shop Floor Display (phase 6). No user session.
- `lib/supabase/server.ts`: user client (RLS applies). Use it by default.
- `lib/supabase/admin.ts`: service role, which **bypasses RLS**. Use it only for auth-admin calls (invites) and the display route. The display route must return only the allow-listed `DisplaySnapshot`.
- `supabase/migrations/`: schema, RLS, triggers. Add new files and never edit an applied migration once it's deployed.
- `supabase/seed/data.ts`: the v1 §17 snapshot, transcribed literally. `generate.ts` produces `supabase/seed.sql`.
- `tests/db/`: RLS and DB tests (Vitest project `db`).
- `lib/data/world.ts`: `loadWorld(viewer)` loads everything a console page needs (once per request), converts times to shop-local and builds domain objects plus `versions` (row id → version for optimistic writes). Cost fields are only queried for the Owner.
- `app/(console)/builds/actions.ts`: all build editing. Pattern: `run(async () => { const c = await context(); …domain check…; await updateRow(db, table, id, version, patch) })`. Multi-row changes use the RPCs in `supabase/migrations/20261002000100_build_rpcs.sql` (`create_build`, `save_plan`, `set_baseline`, `rework_item`, `add_parts`, `add_stage`; SECURITY INVOKER so RLS applies).
- Forms: `ActionForm` submits via `onSubmit` so a refused save keeps the user's input. Dialogs use native `<dialog>` (`components/ui/dialog.tsx` trigger-based, `components/ui/modal.tsx` state-controlled).
- `lib/actions/common.ts`: shared server-action plumbing (`context(roles)`, `run`, `updateRow`, `UserError`, `formObj`). Use it for every new action file.
- **Phase 3.5 (task queue & employee display):**
  - `domain/queue.ts` lays a person's queue on the clock (`layoutQueue`, `dayRow`, `daySegments`, `checkStart`). `domain/gamification.ts` handles the department board and badges. `domain/display.ts` holds the strict `DisplaySnapshot` schema and `buildDisplaySnapshot`.
  - `queue_tasks.position` is a fractional key (`fractional-indexing`, byte order, `collate "C"`). A reorder writes only the moved row. Use `generateKeyBetween(prev, next)`.
  - A queue task linked to a part-step shares its status in both directions (D10). The queue actions update the work item, and `updateWorkItem` updates the queue task.
  - Display route: `GET /api/display/[token]/snapshot` → `lib/display/snapshot.ts`. Service role, token checked by SHA-256 hash, world built with `seesCost=false`, output parsed through `DisplaySnapshot`. The TV page `/display/[token]` refetches on realtime pings and polls every 10 s.
  - Photos live in the private Storage bucket `people-photos`, read through signed URLs (`lib/photos.ts`). They're cropped to a 512 px JPEG in the browser.
  - New tables after the first migrations get `private.standard_triggers(tbl)` and `private.member_policies(tbl)`.

## Conventions and decisions

- **Cost lives only in owner-only tables:** `settings_cost`, `people_cost`, `hour_log_cost`, and the views `work_item_cost` / `project_labour`. RLS blocks them for Supervisors at the database. Never add a cost column to a shared table. Audit rows for these tables are `sensitive` and owner-only.
- **Writes are row-level, with optimistic concurrency:** `update … .eq("id", id).eq("version", v)`. If zero rows come back, show "Someone else changed this — reload and try again." The `touch_row` trigger bumps `version` and `updated_at`.
- **Audit:** the generic trigger logs every insert, update and delete with the actor, role and a before → after diff. Domain actions with readable labels (rebaseline, rework…) call `rpc('audit_action', …)`. Seeding sets `app.skip_audit = 'on'`.
- **Realtime:** a statement-level trigger calls `realtime.send({table, op}, 'changed', 'kynetik-changes', false)`. The message never carries row data, so clients refetch through their own permission path.
- **Time:** the DB stores `timestamptz`. The domain works in shop-local wall-clock `YYYY-MM-DDTHH:mm` and converts at the edges with `settings.calendar.timezone`.
- **Day hours** are derived from the shift (D2) with `dayHours(calendar)`. There is no separate setting.
- **Invite-only auth (D6):** the `invitations` row and the auth-user trigger create the `profiles` row with its role. Signed-in users without a profile see `/no-access`. The DB refuses to remove the last active Owner.
- **Parts are keyed by id (D5):** renaming keeps history.
- **Messages:** user-facing wording comes from spec §9/§15, collected in `domain/messages.ts`; tests lock it.
- **Domain API:** `makeCalendar(settings)` → `wh / norm / addWH / firstWork`; `schedule`, `forecast`, `health`, `boardSort` (schedule.ts); `applyStatus`, `validateWorkItem`, `rework`, `bulkAssign`, `diffPartsList`, `projectAfterChange`, `startBuild` (work.ts); `findTechConflict`, `conflictMessage`, `techDoubleBookings`, `planClashes` (conflicts.ts); `alerts`; `techStats`/`leaderboard`; floor and cost helpers. Fixtures in `domain/__tests__/fixtures.ts` load the §17 seed. Open interpretations I1–I10 are in PLAN.md §0. The v1 read-only banner said "Can interact", which is a v1 platform term, so v2 says "Ask the Owner for Supervisor access."
- **UI / brand** (Brand Guidelines Rev 03, Sep 2026). Tokens are in `app/globals.css`.
  - Palette: Black `#202020` (ground), Carbon Grey `#353535` (lines), Foster White `#ECECEC` (ink), Vintage Yellow `#E9BE5F` (accents: hairlines, tags, numerals, never fields), Olive `#808000`. `ok`/`warn`/`bad`/`cool` are functional status colours only.
  - Type, three tiers. **Broche** headlines: uppercase, weight through scale and tracking, never bold. Michroma stands in for it, as in the guidelines PDF. Use `.display` and `.eyebrow`. **Helvetica** (Arimo fallback) is for body, labels and tables (default `font-sans`). **IBM Plex Mono** (`font-mono`, `.label`) is for serials, numbers, dates and specs, never body copy. Never mix two faces in one line.
  - Logo: `components/ui/logo.tsx` (`Lockup` default, `Stacked`, `Monogram`). The SVGs in `public/brand/` were traced from the guidelines PDF; swap in the designer's master SVGs when they arrive. Never stretch, rotate, recolour or add effects. The favicon is `app/icon.svg`.
  - Copy: third person, state the specification, no exclamation marks, no emoji.
- **Commits** must not mention model names.
